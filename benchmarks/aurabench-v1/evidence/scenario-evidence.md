# AuraBench-v1 场景证据与现实性审阅材料

版本：PR23 设计冻结稿
检索日期：2026-08-27
适用目录：`benchmarks/aurabench-v1/catalog.yaml`

## 当前状态

目录中的 48 对任务都是待实现设计，尚未声称可以运行，也没有写入 static/dynamic YAML。当前机器校验只负责来源标签覆盖、数据切分、负对照和既有 pilot 身份绑定；它不能证明 `realism_basis` 里的自然语言论断。PR24 补齐运行语义后，PR25 至 PR28 再逐族实现并机器检查 static/dynamic 是否只改变一个因素、负对照是否保持答案不变。实现完成仍要经过两名独立审阅者检查，人工审阅不能由自动校验代替。

这里的来源承担三种不同作用。真实家庭数据用于确认居民移动、多人活动重叠、传感器缺口和设备状态变化确实存在；已发表的智能家居基准用于确认状态核验、隐式意图、不可执行请求和时间依赖是可评价的研究问题；安全和访问控制材料用于约束权限与安全响应。任何单一来源都不能同时证明事件会发生以及唯一正确的处置方式。

## 场景进入 YAML 前要经过的检查

1. **来源检查**：每对任务至少引用两个来源，所需证据标签必须能由这些来源覆盖。只引用预印本不能通过。
2. **能力检查**：任务只能使用 Aura 默认注册表已有的灯、空调、窗帘、风扇、摄像头和传感器。摄像头与传感器是只读设备，场景不得伪造写能力。
3. **因果检查**：dynamic 版本只改变一个干预因素。干预必须发生在可观测的执行阶段，并留下物理事件或观测投影变化。
4. **反事实检查**：static 与 dynamic 共享初始状态、用户目标、基础时间线和 seed。负对照中的无关变化不能改变正确答案。
5. **现实性检查**：设备效果不能早于命令，居民和设备不能出现在不存在的房间，替代设备必须真的能满足同一目标。
6. **评价检查**：oracle 描述家庭可观察结果和安全约束，不依赖 Aura 私有的 Agent 名称或内部事件才能成立。
7. **人工检查**：两名审阅者分别判断场景是否可信、正确策略是否允许合理替代、时间窗是否有依据。分歧保留原记录并交给第三人裁决。

## 来源及其可承载的结论

### SimuHome，ICLR 2026

论文和官方仓库把状态查询、隐式意图、显式控制、时间调度分成可执行任务，并同时设置可行与不可行请求。设备动作产生连续环境反馈，计划执行前后的设备状态可能变化。Aura 借鉴这些任务维度和可验证目标，不复制其 episode，也不引入当前注册表没有的洗衣机、洗碗机等设备。

来源：[ICLR 2026 官方页面](https://iclr.cc/virtual/2026/poster/10010052)，[论文预印本](https://arxiv.org/abs/2509.24282)，[官方仓库](https://github.com/holi-lab/SimuHome)

### HomeBench，ACL 2025

HomeBench 区分有效、无效以及混合有效性的单设备和多设备指令。它支持 Aura 把不可执行请求和部分可执行请求纳入评价，也提醒我们不能用错误设备凑出一个看似有动作的答案。该数据集主要评价指令到 API 的映射，不支持 Aura 对动态执行过程的结论。

来源：[ACL Anthology](https://aclanthology.org/2025.acl-long.597/)

### PersonalHomeBench，2026 预印本

这项工作要求反事实只修改一个主因素，同时生成答案改变和答案不变的任务，并检查物理、时间和家庭实体的一致性。它直接支持 Aura 的 static/dynamic 配对和负对照结构。论文仍是预印本，而且大量家庭内容由生成流程构造，因此不能单独用来证明某个生活情节常见。

来源：[arXiv](https://arxiv.org/abs/2604.16813)

### CASAS 与 ARAS 真实家庭数据

CASAS 提供单人、多人和长期公寓数据；ARAS 在两个真实住宅中连续记录两位居民和 27 种活动。两类数据支持居民换房间、活动切换、多人同时在家和无关居民活动等事件。它们没有记录哪一种 Agent 仲裁规则正确，所以只用于构造状态轨迹，不用于决定权限优先级。

来源：[CASAS 官方目录](https://casas.wsu.edu/datasets/)，[ARAS 论文](https://eudl.eu/doi/10.4108/icst.pervasivehealth.2013.252120)

### CASAS-SW 真实世界可穿戴数据

CASAS-SW 文档明确记录夜间和充电造成的数据缺口、位置值在两次读数间保持旧值、活动标签晚于实际活动出现等现象。它支持“旧观测仍被 Agent 看见”这一故障形态。具体延迟秒数不能从该数据直接搬到 Aura，PR24 必须把延迟作为校准参数并分别报告。

来源：[官方数据说明](https://casas.wsu.edu/datasets/smartwatch/)

### 真实家庭照明与供暖冲突研究

Niemantsverdriet 等人在家庭环境中观察到偏好、活动和态度三类照明冲突，文中包含阅读、睡眠、看电视、亮度和色温差异。Sovacool 等人的 100 户英国 Living Lab 研究记录了温度设置和供暖实践冲突。这些材料支持阅读者与睡眠者、共享空间亮度以及温度偏好任务，同时也说明系统不能默认总有一个固定居民应该获胜。

来源：[照明冲突研究](https://link.springer.com/article/10.1007/s00779-016-0998-5)，[供暖冲突研究](https://doi.org/10.1016/j.erss.2020.101566)

### 智能家居 routine 冲突用户研究

Zaidi 等人对 197 名当前或潜在智能家居用户进行情景调查，结果没有发现对所有上下文都满意的统一冲突解决策略。Aura 因而只评价场景中明确声明的家庭协议，不把 last-write-wins、房主永远优先或平均偏好写成普适答案。

来源：[论文 DOI](https://doi.org/10.1145/3581997)

### NIST 角色与最小权限指导

NISTIR 8259A 的逻辑访问章节要求系统区分授权和未授权用户，支持角色层级、允许的设备动作、临时角色和最小权限。它支持 Aura 实现 owner、adult、child、guest 的权限检查，但不规定家庭成员之间的社会优先级。具体权限必须由 household contract 明示。

来源：[NIST 官方页面](https://pages.nist.gov/FederalProfile-8259A/technical/logical/)

### SOTERIA 与 Home, SafeHome

SOTERIA 用形式化属性检查烟雾报警和多个自动化之间的危险交互；Home, SafeHome 把并发 routine、设备失败和连接中断列为家庭自动化进入不安全状态的主要来源。这两项工作支持安全事件抢占普通舒适计划、执行中设备故障和跨 routine 冲突。它们不规定住宅灯必须设为 100% 或必须在某个固定秒数内完成，Aura 的具体亮度与时间窗仍要作为场景协议接受人工审阅。

来源：[SOTERIA](https://www.usenix.org/system/files/conference/atc18/atc18-celik.pdf)，[Home, SafeHome](https://www.usenix.org/system/files/hotedge19-paper-ahsan.pdf)

### ARGUS 真实设备状态数据

ARGUS 的公开数据记录五个真实住宅中的 IoT 设备状态变化，其中三个住宅有四名居民。它可用于核对无关设备变化、摄像头状态变化和多居民背景活动是否符合真实遥测形态。数据集面向入侵检测，没有提供设备故障后的正确恢复动作。

来源：[官方数据仓库](https://github.com/TRUST-TUDa/argus-data)

## 已排除或修订的设计

- **不新增门锁、烤箱、洗衣机、水阀和洗碗机任务。** 这些设备在其他论文中常见，但 Aura 默认注册表没有对应状态机。把它们写进 YAML 会制造无法执行的纸面场景。
- **不把风扇故障自动改成空调。** 风扇提供气流和体感变化，空调改变温度，两者不总是同一用户目标。新目录改为：没有等价设备时明确报告不可恢复。
- **不把父母优先于儿童写成通用社会规则。** NIST 支持角色权限与最小权限，不支持固定家庭偏好。测试只检查场景声明的权限和家庭协议。
- **不声称烟雾时全亮是法规要求。** 来源支持烟雾报警必须保持有效以及安全自动化不能被普通 routine 破坏。具体照明动作是 Aura 家庭策略，需要人工审阅并在论文中按策略报告。
- **不从真实数据估计任意延迟秒数。** CASAS-SW 支持数据缺口和旧值现象，延迟强度由 validation split 校准，test split 冻结后不得调整。
- **不把无关变化当作难度填充。** 每族只保留一对负对照，并明确要求正确结果不变；如果运行结果变化，应判定 Agent 过度反应或场景实现泄漏。

## 许可与复用边界

仓库只保存书目信息、证据摘要和 Aura 自己的场景设计，不保存或改写外部论文的 episode、用户原话和受限数据。每条外部来源的完整地址、用途和限制记录在 `../sources.json`。需要复核原文时应从来源页面读取，并遵守对应许可和数据访问条件。
